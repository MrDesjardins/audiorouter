# Tool guides built from the real property window

Status: implementation authorized by the owner on 2026-10-29; execution is
tracked in the [active plan](../active/current.md#owner-revision-after-gate-review-2026-10-29).
Keep the stable plan here as the feature contract.

## Outcome

Every tool page on <https://audiorouter.org/tools.html> gains short clips of the
**real Properties window** of that tool, shown alongside the settings examples
(owner revision 2026-10-29: the existing animations and diagrams stay, because
they are fun to play with and show the effect of a setting). Clips (5 to 10
seconds, no narration) show each property being changed on a fake sound, with
the real audio that results. The page text explains what the viewer is seeing. A dozen or
more clips on a page is fine, as long as every property is covered.

Owner review of the first Gate capture rejected the canvas-including frame and
authorized the full all-tool recording. The corrected framing is portrait 9:16
and contains only the selected tool's Properties panel. Keep its top live visual
or status area visible through playback; briefly reveal a lower control when it
changes, then return to the top while audio continues. Cover all 37 node kinds
and map every exposed property to a recording or a documented non-audible
exception. Never imply that a device, remote peer, arbitrary plugin, or hardware
was actually used by a synthetic fixture.

Example: the Gate page plays a clip of speech-like bursts over room noise. The
Threshold slider moves, the level meter shows the signal falling below and rising
above it, and the audio gets quieter and louder to match. The text beside it
explains what happens and how to choose the setting. Advanced EQ shows one band's
frequency being swept over noise, so the viewer hears and sees where the change
lands.

## What exists today

- The current guides are conceptual diagrams with a synthetic Web Audio preview
  ([all-tool guide audio](../archived/2026-10-15-all-tool-guide-audio.md),
  [synchronized playback](../archived/2026-10-15-synchronized-tool-guide-playback.md)).
  They are interactive and the owner wants to keep them. What they lack is
  the look of the real application, which the new clips supply. The diagrams stay
  as they are.
- Spec **UI-20** requires "accessible conceptual signal illustrations" and says
  never to present them as measured DSP. That stays true for the diagrams. The
  clips are a second, clearly different kind of content (real window, real
  processing), so UI-20 needs an **addition**, not a replacement: the clips are
  labelled as recordings of the real application, and the diagrams stay labelled
  as conceptual. The addition and its tests go in a decision record plus spec
  update when the plan is promoted.
- The pages are generated by `site/generate-guides.mjs` from
  `site/guide-content/*.json` into `site/tools/*.html`. The domain has 37
  addable node kinds plus the visual Group: 38 guide pages plus the tools index.
- The homepage video already follows a poster-first, muted, `+faststart` H.264
  recipe in `site/README.md`. That recipe is silent; these clips carry audio, so
  they need their own rules below.
- The UI test harness can drive the real React UI against a real or simulated
  backend in Edge (`ui/e2e/real-backend.ts`, the route harness, and
  `readme-screenshots.pw.ts` for opt-in generators that write into the repo).

## Approach

### 1. Fake sounds (fixtures)

Small, deterministic, license-free sounds generated by a seeded script, so there
is nothing third-party to clear and the same clip can be rebuilt. Committed as
short WAV files, or regenerated in the pipeline.

| Fixture | Used to show |
| --- | --- |
| Speech-like bursts (modulated noise, quiet gaps) over low room noise | Gate, Expander, Spectral Gate, Denoise, Duck, Compressor |
| Pink noise | EQ tools, Bass and Treble, FIR, filters |
| Synthetic drum loop (kick, snare, hat) | Compressor, Limiter, Delay, Time Shift |
| Sine sweep and tone steps | Pitch, Test Signal, level tools, meters |
| 50/60 Hz hum plus a voice-like tone | Dehum |
| Click train | Declick |
| Two distinct sounds (for example low and high tone) | Mixer, Input Switch, Output Switch |

### 2. One timeline for picture and sound

A browser screen recording has no audio, and recording speakers would not be
reproducible. So each clip is described by a **timeline** and produced twice from
it, in sync:

1. **Audio:** render the fixture through the real processing at the real
   parameter values over time, offline, to a WAV. This is the tool's actual DSP,
   not a Web Audio imitation.
2. **Picture:** drive the real Properties window in Edge with the same timeline
   (the slider moves at 2.0 s, the toggle flips at 5.5 s) and record frames.
   Meters and reduction readouts come from the same render's telemetry, replayed
   to the UI at its normal 20 Hz rate, so what moves on screen is what the audio
   did.
3. **Mux** picture and audio into the final file with ffmpeg.

A clip manifest (JSON) holds: tool kind, fixture, the parameter changes with
times, duration, and the caption lines shown beneath it on the page.

Open question, to settle in the first spike: is there an offline render path in
the engine crate that applies a prepared graph to a file with parameter
automation and returns telemetry? If not, a small test-only example binary has to
be added. It must reuse the production processors, otherwise the video shows
something the app does not do (see the validated lesson about judging audio with
the real harness).

### 3. Coverage rule: every property

A generated inventory lists every parameter of every tool from the domain
parameter specs. The manifest set must reference each one, or carry a written
exemption (for example "device selection, not audible"). A check fails when a
property exists without a clip or exemption, so a future new property cannot be
forgotten.

### 4. Non-audible properties

Tools whose settings choose a device, an application or a file (Physical Input,
Physical Output, Application Capture, Endpoint Loopback, Plugin, Network Send and
Receive, Recorder, Groups) have no sound-changing property to demonstrate. They
still receive a portrait Properties-only UI recording or representative still
that covers their settings. Keep these silent or use only independently
processed audio where relevant; label the scope so viewers cannot mistake a
synthetic playback for device, network or plugin qualification. Record motion
that helps explain the property, such as the Recorder meter or Network pairing.

### 5. Page layout

Per tool page: the existing intro, diagram and interactive preview stay where
they are. Add a new "In the app" part: the real Properties window screenshot with
a numbered property list, then one section per property or group of related
properties, each with a clip and two or three sentences, placed with the
examples of settings. Where the interactive preview already covers a setting, the
clip section links back to it ("try it yourself above") rather than repeating it.
Writing follows the website voice rules in `AGENTS.md` (plain, specific, direct).

## Clip specification

- Length 5 to 10 seconds. Portrait 9:16. Record only the selected Properties
  panel; the canvas, tool card, other panels and app chrome are outside the
  frame. Keep the panel's top live visual/status area visible during playback.
  At a parameter change, show the relevant lower control briefly and return to
  the top while sound continues. Check that values and labels remain readable.
- Dark theme only. The real app is dark by default; adding the light and
  high-contrast themes would triple the files for little teaching value.
- H.264 video with AAC audio, `+faststart`, `preload="none"` with a poster
  image, native controls, **no autoplay**. A viewer presses Play, as requested.
- Size budget per clip (target 400 KB to 1 MB). Page budget to be set from the
  longest page; measure GitHub Pages size and bandwidth limits against the full
  set before committing to the count.
- Burned-in text is minimal (at most a small label such as "below threshold").
  The explanation is page text, so it stays accessible and searchable.
- Accessibility: visible controls, keyboard operable, a text description of
  what is seen and heard under each clip, and nothing that depends on audio
  alone. Reduced-motion users get the poster and the description (they can still
  press Play). Offscreen clips do not start by themselves.
- Firefox is the owner's default browser (validated lesson): the Firefox sweep
  with a real click on Play must show the clip playing with audible output
  before publishing. H.264/AAC plays in Firefox on Windows; confirm rather than
  assume.

## Order of work

1. **Gate framing revision (complete).** The first Gate render proved the
   production engine path and basic sync, but the owner rejected its
   canvas-inclusive frame. Three replacement clips use the approved portrait,
   Properties-only framing, briefly show the changed value, then return to the
   live top visual. Firefox playback remains unverified.
2. **UI-20 and scope decision (recorded).** The diagrams stay conceptual and
   unchanged. [UI-20](../../spec/09-interface.md#requirements)
   now distinguishes labelled real-UI/production-DSP recordings and
   configuration-only recordings. See the
   [owner decision record](../active/evidence/2026-10-29-tool-guide-capture-decision.md).
3. Build the pipeline: inventory all 37 node kinds (and visual Group) plus
   their exposed properties; fixture generator; clip manifest and property
   coverage format; recorder script under `tools/site/`, coverage check, and
   page-generator changes (`generate-guides.mjs` and guide content).
4. Record all tools and property groups in waves by value: dynamics, EQ, time
   and pitch, clean-up, routing and configuration tools. Map every exposed
   property to a recording or a documented exception.
5. Website review as a whole: page weight, load time, phone layout, Firefox
   playback and top-visual legibility. Publication remains a separate gate.

## Validation matrix

| Check | Environment |
| --- | --- |
| Fixture generator is deterministic (same bytes twice) | Portable |
| Offline render matches the live engine on the same input and settings | Windows, engine test |
| Coverage check: every tool property has a clip or an exemption | Portable, CI |
| Audio-picture sync: marked event times in the final file match the timeline within a frame | Pipeline check |
| Clip size and duration limits | Pipeline check |
| Each page: no layout shift, readable at phone width, controls reachable by keyboard | Edge/Playwright |
| Real click on Play and audible output | Firefox sweep and Edge |
| Written descriptions present for every clip | Portable check |

## Risks and decisions

- **The recording uses the real UI in a browser harness, not the packaged
  window.** The React components are the same code. The title bar and window
  frame are missing. Say so, and decide whether that is acceptable or whether a
  capture of the packaged WebView2 app is wanted (much harder to automate).
- **Clips go stale when the UI or a default changes.** Keep recording a script,
  stamp each clip with the UI revision and the parameter-spec hash, and fail a
  check when the hash changes so a clip is regenerated, not forgotten.
- **Audio-picture drift.** One clock drives both from the same timeline.
- **Site size and bandwidth.** Measure before committing to a large number of
  clips; lazy load and posters keep first load small.
- **Cost of the spike.** Offline render may require a new test-only binary.
- **Spec addition.** UI-20 forbids presenting illustrations as measured DSP, which
  still holds for the diagrams. Adding the clips needs a labelled, separate
  clause (real application, real processing) so the two kinds of content cannot
  be confused. Do it in the decision record, not as a side effect.
- **Page length.** Diagram plus clips on one page gets long. Keep one clear
  order (explanation, diagram, in the app) and check phone width.

## Rollback

The generated pages and the media folder are build outputs. The existing
diagrams are untouched, so reverting the generator change and deleting the media
folder returns each page to its current state. No app, API or storage change is involved.

## Prerequisites

- Owner review of the Gate spike.
- An answer to the offline-render question above.
