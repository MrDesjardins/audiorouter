# Tauri auto-update

Status: future work, not authorized. This plan records what an in-app update
would require, why it is not part of the current release, and the gates that
must pass before AudioRouter downloads or installs a build itself.

## Objective

Let an AudioRouter user move from an installed version to a newer signed build
without finding the release page, downloading the installer, closing the app and
running it by hand. The user always chooses to update; AudioRouter never
replaces a running build silently, never forces a restart during live audio,
and never installs an unsigned or unverified package.

This is separate from UI-18. The current check reads the public GitHub release
list and opens the release page. It never downloads or installs anything.

## Current state and why this is future work

- AudioRouter publishes an unsigned per-user NSIS installer from a manually
  published GitHub prerelease. There is no updater plugin, no signed update
  artifact, and no update manifest or feed.
- SEC-11 requires signed packages and integrity verification before applying an
  update, separate app/driver compatibility, retained rollback artifacts, and
  no forced updates during live sessions.
- The M08 clean-machine install, upgrade, rollback, uninstall and data-retention
  gates are still open. An updater makes those gates load-bearing.
- The desktop app is one process with an embedded backend plus bundled
  `audiorouter-cli.exe`, VST2/VST3 workers and a Stream Deck plugin. The managed
  virtual cable is a separately signed driver package with its own version and
  install flow.
- Release notes currently say "Close AudioRouter before upgrading." A real
  updater has to replace that instruction with a tested close/install/restart
  sequence.
- The project has no code-signing identity. SignPath declined on 2026-10-21;
  Azure Artifact Signing was under consideration. Tauri's updater signature is
  a separate minisign key and does not remove SmartScreen warnings caused by an
  unsigned executable, so OS signing remains a product decision.

## Scope

In scope when authorized:

- A signed update manifest per release channel, generated by the release
  workflow.
- A Windows x64 NSIS update that replaces the desktop app, CLI, workers and
  bundled resources in the existing per-user install folder.
- A Settings → New versions flow with download progress, signature
  verification, a restart prompt, "Later" and "Skip this version".
- Deferral while a session is running or recording; no forced restart.
- Rollback instructions and retained previous installers/configuration.
- Update checks and the header notice continue to work offline and with no
  account.

Out of scope:

- Silent background installation, forced restarts, or updates during live audio.
- Auto-installing the AudioRouter virtual cable driver. Driver updates remain a
  separate signed package with their own compatibility and elevation flow.
- Updating third-party VST plugins or the user's installed Stream Deck copy
  without an explicit action.
- Linux/macOS packaging, portable installs, or a cloud update service that
  receives identifiers or audio data.

## Proposed architecture

1. **Tauri updater plugin (`tauri-plugin-updater`).** It reads a signed JSON
   manifest, verifies the artifact with a public key compiled into the app, and
   downloads the NSIS installer to a temporary file. The app does not hand an
   arbitrary URL from the renderer to the shell.
2. **Release manifest and channels.** The release workflow generates:
   - a signed installer,
   - a `latest.json`-style manifest with version, publication time, notes and
     the Windows x64 artifact URL plus its signature,
   - stable and prerelease channel manifests.
   GitHub's "latest release" URL excludes prereleases, so the manifests need a
   stable HTTPS location. GitHub Pages on audiorouter.org is the cheapest
   option; Cloudflare is an alternative if the site moves there. A release
   workflow may publish the manifest only after the draft release has its
   installer and checksums.
3. **One check, two outcomes.** The existing release-list check already owns the
   header notice, cache and retry behavior. When the updater is authorized, the
   signed channel manifest should become the source of the version, release page
   and download metadata so the app makes one request instead of two. Keep the
   lightweight notice when the user has not opted into downloading.
4. **Shell-owned install.** Add a narrow shell command that starts the verified
   install and reports progress. It accepts no caller-chosen path or URL. The
   renderer only receives progress and state; the backend and audio threads are
   not involved in the download.
5. **Lifecycle.** Before installing:
   - ask the user to stop the session or offer to stop it,
   - refuse to update while a recording is active or a driver operation is in
     progress,
   - close the window and backend cleanly so the single-instance control pipe is
     released,
   - run the NSIS package, then start the new build,
   - keep the previous installer and a configuration/database backup available.
6. **Version compatibility.** The app and the managed cable driver have separate
   versions. The updater must know the minimum compatible driver and refuse or
   warn instead of leaving a new app with a missing/incompatible driver. The app
   must also refresh the bundled Stream Deck plugin resource or prompt the user
   to install it again when its version changes.

## Security requirements

- **Updater signature.** The manifest and installer are signed with a dedicated
  minisign key. The public key is compiled into the app. A missing, malformed,
  or invalid signature aborts the download; the user sees a failure, not a
  retry loop that installs anything.
- **Key custody.** The private key lives outside the repository and outside
  ordinary developer machines; CI uses a protected environment/secret. Define
  rotation and revocation before the first release. A test key is used for
  automated tests.
- **Transport and origin.** HTTPS only, with a fixed allowed host. A
  compromised GitHub release must not be installable without the signing key.
- **Downgrade and replay.** Reject a manifest version at or below the installed
  version, and reject a manifest whose channel or platform does not match.
- **Integrity and atomicity.** Download to a temporary file, verify size and
  signature, then install. Handle a partial download, disk-full, antivirus
  quarantine, sleep during download and a lost connection.
- **Consent and privacy.** The user explicitly starts the download. No
  identifier, audio, route or device information is sent. The existing opt-out
  and channel preference apply.
- **Authorization boundary.** Do not expose install/restart through REST, MCP or
  remote clients. If an API method is ever added it needs session-control
  authorization and an MCP exclusion reason; a remote assistant must not be able
  to replace the desktop build.
- **No rollback to an older insecure build** without a deliberate user action
  and a clear warning.

## User experience

Reuse the existing New versions panel and header notice:

- Status: current, checking, available, download available, downloading,
  verified, ready to install, installing, install failed, restart required.
- Primary actions: "Download and install", "Later", "Skip this version".
- Show version, release date/notes link and download size where known.
- Progress: a bounded progress bar plus downloaded/total bytes; no layout shift,
  and the last good value stays visible through brief gaps.
- Failure copy names the cause (offline, rate-limited, signature failure, disk
  full) and offers a safe retry, not an automatic install.
- Before install: "Audio is running. Stop it and install?" with a cancel path.
- After install: restart prompt; if the user chooses Later, install on next
  normal quit rather than silently restarting.
- Never mix the update action with the "Check now" action; checking remains a
  read-only operation.
- Preserve the header's single-line notice and the UI-17 reserved slots.

## Release pipeline changes

- Build the NSIS installer and updater artifact in the release workflow and
  sign both the OS executable (when signing exists) and the updater artifact.
- Publish a per-channel manifest only for a published, non-draft release with
  the expected installer asset.
- Include SHA-256, release page URL, minimum app version and minimum driver
  version in the manifest.
- Verify the manifest download from a clean machine and from the previous
  public release before advertising the update.
- Keep the manual draft-review step and human publish decision. No push-
  triggered production publication.
- Add a kill switch: a channel manifest can be withdrawn or marked unavailable
  without shipping a new client.

## Qualification matrix

Automated:

- Manifest parsing: channel, platform, version, URL, notes, hashes, signatures.
- Signature valid, missing, malformed, expired/rotated key, wrong installer.
- Version comparison: same, older, newer, prerelease-to-stable, downgrade.
- Feed failures: offline, timeout, 403/429, malformed JSON, empty channel.
- Download: slow, interrupted, resumed or restarted, disk full, size mismatch,
  hash mismatch, sleep/resume.
- Lifecycle: session stopped, session running (deferred), recording active
  (refused), driver operation active (refused), quit/restart ordering.
- Existing UI-18 tests remain offline; the update flow uses a local test feed.

Windows qualification (VM first, then a real clean machine):

- Install the previous public release, then update to the candidate: routes,
  settings, recordings, plugin links and startup preference survive.
- Standard-user install, per-user folder, no elevation unless the separate
  driver flow requests it.
- Missing WebView2, low disk, offline, proxy, antivirus, SmartScreen, interrupted
  install, install while the old build is running.
- Rollback to the previous installer; data retention after uninstall.
- Arbitrary code cannot make the shell install a URL or path it chooses.
- The embedded UI and all sidecars are newer than the installed build.
- The installed Stream Deck plugin and managed cable driver report compatible
  versions.

## Rollout

1. Signing and feed decisions, protected key setup, test key in CI.
2. Internal-only updater behind a developer preference; no public download.
3. Beta/prerelease channel for volunteers; collect failures without personal
   data.
4. Stable channel only after M08 upgrade/rollback and clean-machine gates pass.
5. Keep the old release page download path until the updater has a full release
   cycle of evidence.

## Rollback and incident response

- Keep the previous installer and checksums on the release page.
- Back up the database and session files before install; restore on failure.
- If a bad build ships, withdraw the channel manifest first, then publish a
  fixed build. Never rely on a forced downgrade.
- Preserve redacted logs; record the version, channel, manifest, signature and
  failure stage. Do not log signing secrets or user audio.

## Decisions needed before implementation

- OS code signing (Azure Artifact Signing or another provider) and budget.
- Updater signing key owner, storage, rotation and CI access.
- Feed host: GitHub Pages on audiorouter.org, Cloudflare, or another origin.
- Channels: prerelease only at first, or stable + prerelease.
- Whether download starts automatically after consent or only on an explicit
  "Download" click.
- Whether "Later" installs on next quit.
- How the managed cable driver version is checked and what the app does when it
  is too old.
- Whether the Stream Deck plugin is refreshed automatically or the user is
  prompted to reinstall it.

## Acceptance criteria

- A user on the previous public release can update from inside the app, with a
  signed manifest and installer, and keep routes, settings, recordings and
  startup preference.
- An unsigned, tampered, downgraded or wrong-platform artifact never installs.
- No update starts while a session or recording is active; the user is asked
  first.
- A failure at every stage leaves the installed version working and reports a
  clear reason.
- The release workflow and runbook produce the manifest and artifact
  reproducibly, and a human still reviews the draft before publication.
- SEC-11 and the M08 upgrade/rollback gates have recorded evidence before the
  feature is described as available to ordinary users.
