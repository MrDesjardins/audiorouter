## How to use this document

Each finding has the same fields:

- **Severity**: High (wrong audio, lost data or a broken feature in normal
  use), Medium (wrong in a reachable but less common case, or a robustness or
  performance risk), Low (latent, cosmetic or dead code).
- **Confidence**: *Confirmed by reading* (the code path is unambiguous),
  *Confirmed by simulation* (reproduced outside the product), or *Needs
  reproduction* (plausible from the code; write the failing test first and
  drop the finding if it passes).
- **Where**, **What is wrong**, **Failure scenario**.
- **Why it was built that way**: the cause, so the repair removes the cause
  and not only the symptom.
- **Fix** and **Regression test** (the test must fail before the fix, AGENTS.md
  "Done means exercised", rule 6).
- **Prevention**: the structural change that stops the same class of bug.

Rules for whoever repairs a finding:

1. Write the failing test first. If it does not fail, record that here and
   stop: the finding was wrong.
2. One finding per commit, with its test. Follow AGENTS.md (format, Clippy,
   `source_combinations.rs`/`tool_combinations.rs`, REST/MCP parity).
3. Mark the finding `Fixed in <commit>` or `Rejected: <reason>` in the index.

## Audio media

### MEDIA-1 — Soundboard and FIR Filter sounds are not treated as media references

- **Severity**: High. **Confidence**: Confirmed by reading.
- **Where**:
  - `crates/control/src/audio_media.rs`, `dispatch_audio_media_delete`
    (the `referenced` check, about line 520): only `NodeKind::AudioFile`
    nodes with a `mediaId` parameter count.
  - `crates/storage/src/lib.rs`, `prepare_bundle_export` (about line 3028),
    `restore_session_bundle` missing-asset count (about line 3345) and
    `keep_session_audio_media` (line 217): only the parameter named
    `mediaId` is read.
  - The Soundboard stores its sounds as `slot1MediaId` … `slot9MediaId` and
    `slot1Set` … `slot9Set` (an array of media IDs or a library category
    name): see `prepare_soundboard` in `crates/engine/src/lib.rs` and
    `load_soundboard_media_with` in `crates/control/src/sound_library.rs`.
- **What is wrong**: four places decide "which stored sounds does this
  session use" by looking for one parameter name, and one of them also
  filters on one node kind. None knows the Soundboard's slot parameters, and
  the delete check ignores the FIR Filter's impulse response.
- **Failure scenarios**:
  1. A user uploads a sound, assigns it to a Soundboard pad, and
     `audioMedia.delete` (UI, REST or MCP) removes it without the "still
     referenced by a session" error. The pad is silent on the next Play.
     The same happens to a FIR Filter's impulse response, and that node then
     refuses to play ("AudioRouter no longer has …").
  2. A session bundle exported from a route with a Soundboard contains no
     uploaded pad sounds. Imported on another PC, every such pad is empty and
     the import report does not count them as missing.
  3. A sound stored with a 24-hour expiry (the temporary voice take import)
     and placed on a pad is not made permanent when the session is saved, the
     defect fixed for Audio File nodes on 2026-10-24.
- **Why it was built that way**: the media store was written for the Audio
  File node, whose single parameter is `mediaId`. The FIR Filter reused the
  same parameter name, so the name-only checks kept working by accident. The
  Soundboard (2026-10-29) introduced new parameter names and its own loader,
  and nothing forced the older checks to be revisited: they are string
  comparisons, not an exhaustive `match` on `NodeKind`. This is the same
  class as the "hand-made list a new kind can miss" lessons of 2026-10-29
  and 2026-10-31 in AGENTS.md.
- **Fix**: add one function in `crates/domain` that returns every stored
  media ID a node references, written as an exhaustive `match node.kind`
  with no `_` arm (Audio File and FIR Filter: `mediaId`; Soundboard: each
  `slotNMediaId` and each string in an array `slotNSet`; skip IDs with the
  `lib:` sound-library prefix, which are files on disk, not database rows).
  Add a `Session`-level helper that collects them. Replace the four checks
  above with it. The delete check must not filter on node kind.
- **Regression tests** (each fails today):
  - control, through `ControlPlane::dispatch`: upload a sound, put it in
    `slot1MediaId` of a Soundboard, call `audioMedia.delete`, expect the
    "still referenced" error; repeat with a `slot2Set` array and with a FIR
    Filter `mediaId`.
  - storage: export a bundle for a session with a Soundboard pad that uses an
    uploaded sound, import it into an empty database, and require the sound
    to exist and the pad to load.
  - storage: save a session whose Soundboard pad uses an expiring sound and
    require `expires_at` to be `NULL` afterwards.
- **Prevention**: a test in `crates/domain` that walks `NodeKind::ALL` and
  the parameter schema (`node_parameter_schema`) and fails when a parameter
  whose name ends in `MediaId` or `Set` is not returned by the new function.

## Built-in DSP (`crates/dsp`)

### DSP-1 — Stereo limiter shares one gain across channels processed in sequence

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/engine/src/lib.rs`, `ProcessingStage::Limiter` in
  `RuntimeGraph::process` (about line 10497) calls
  `PeakLimiter::process_channel(channel, samples)` for the whole left plane,
  then the whole right plane. `crates/dsp/src/lib.rs`, `PeakLimiter::process_one`
  keeps a single `self.gain` for all channels.
- **What is wrong**: the gain envelope is a function of time, but it is
  advanced through 128 left samples and then 128 right samples. Three
  effects follow: (1) release is applied twice per frame, so a stereo
  limiter releases twice as fast as its `release_ms`; (2) a left peak late in
  a block reduces the right channel from the start of that block (too early)
  but the left channel only from the peak; (3) a right-only peak reduces the
  right channel at once and the left channel one block late. Left and right
  therefore get different gain at the same instant: the image shifts and the
  final clamp clips the channel that was not reduced in time.
  `process_interleaved` has the first effect too (release per sample, not per
  frame).
- **Failure scenario**: stereo music with a hard-panned transient through a
  Limiter at -6 dB: the level difference between channels changes for one
  block around each transient, and measured release is half the setting.
- **Why it was built that way** (inferred from the code, not from history):
  the limiter keeps one shared gain, which is right for interleaved
  processing. The Compressor and Gate have `process_planar_linked` for the
  engine's planar blocks; the Limiter has only a per-channel entry point that
  kept the shared gain, and its tests check the ceiling, which the clamp
  always satisfies.
- **Fix**: add `PeakLimiter::process_planar_linked(left, right)` that, per
  frame, takes the larger magnitude of both channels, updates the gain once,
  and applies it to both delayed samples. Use it for stereo blocks; keep
  `process_channel` for mono. Apply the release once per frame in
  `process_interleaved` as well.
- **Regression tests**: in `crates/dsp`: (a) feed a stereo block with an
  impulse on the right at frame 5 and a constant 0.5 on the left, and require
  identical gain on both channels at every frame; (b) measure the time for
  the gain to recover 63 % after a peak in stereo and require it to match
  `release_ms` within 5 %, the same as mono. In
  `crates/engine/tests/planar_kernels_match_reference.rs`: the stereo
  Limiter stage must equal the interleaved reference.
- **Prevention**: every stereo-capable dynamics processor gets the same
  "mono and stereo release times are equal" and "both channels get the same
  gain" test, written once as a generic helper.

### DSP-2 — Limiter lookahead does not hold the gain for the delayed peak

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/dsp/src/lib.rs`, `PeakLimiter::process_one`.
- **What is wrong**: the gain drops when a peak *enters* the delay line and
  then starts releasing at once (`if desired_gain >= self.gain` is always
  true after the `min` on the line above). When the peak *leaves* the delay
  `lookahead` later, the gain has already recovered part of the way, so the
  sample exceeds the ceiling and the final `clamp` hard-clips it. With 5 ms
  lookahead and 100 ms release the gain has recovered about 5 % of the
  reduction (about 10 % in stereo, see DSP-1). With zero lookahead the peak
  sample itself is released once before it is scaled, so it is clamped too.
- **Failure scenario**: any peak above the ceiling is flattened by the clamp
  (audible distortion on loud voice) instead of being scaled.
- **Why it was built that way**: the comment says "attack is immediate;
  release follows a finite exponential envelope". The lookahead was added as
  a delay only; the tests assert that output never exceeds the ceiling, which
  the clamp guarantees regardless of the envelope.
- **Fix**: keep the gain at or below the minimum required by every sample
  still in the delay line (a hold counter of `lookahead_frames` reset on each
  new minimum, or a sliding-window minimum), and release only after the hold
  expires. Skip the release on the sample that sets a new minimum.
- **Regression test**: feed a single full-scale impulse into a limiter with
  5 ms lookahead and a -6 dB ceiling while recording `output / delayed input`;
  require the ratio at the impulse to equal the ceiling gain within 0.1 dB
  and require that the clamp branch was not what limited it (compare against
  an unclamped computation, or expose a debug counter of clamped samples and
  require zero).
- **Prevention**: limiter tests must assert the *gain* applied, not only the
  output bound.

### DSP-3 — An infinite sample latches the mono compressor

- **Severity**: Low. **Confidence**: Confirmed by reading.
- **Where**: `crates/dsp/src/lib.rs`, `Compressor::process_interleaved`
  (used by the engine for mono blocks and for split stereo).
- **What is wrong**: the detector uses `sample.abs()` before the finite
  check. `+inf` gives `level_db = inf`, `envelope_db` becomes `inf`, and
  `coefficient * inf` stays `inf` for ever. The reduction is infinite, the
  gain is zero (or NaN at ratio 1, repaired to zero), and the compressor is
  silent until `reset`. NaN is ignored by `f32::max`, so only infinities
  latch. `process_planar_linked` sanitizes first and does not latch.
- **Failure scenario**: a plugin or a float capture device emits one `inf`
  sample ahead of a mono Compressor in the same chain (the graph sanitizes
  only at the end of `RuntimeGraph::process`): the route goes silent and
  stays silent.
- **Why it was built that way**: the planar path was written later with the
  sanitize-first pattern; the older interleaved path was not updated, and the
  non-finite tests cover output finiteness for one block, not recovery on the
  next block.
- **Fix**: compute the detector peak from sanitized inputs in
  `Compressor::process_interleaved` and `Gate::process_interleaved`, and
  clamp `envelope_db` to a finite range.
- **Regression test**: process `[inf]` then 1 000 samples of a -20 dBFS sine
  through a mono compressor and require non-zero output and a finite
  `gain_reduction_db`.
- **Prevention**: a shared test helper that feeds `inf`, `-inf` and NaN to
  every processor and then requires normal output on the following block.

### DSP-4 — Running-sum RMS meters report NaN after signal then silence

- **Severity**: Low (not used by the app today). **Confidence**: Confirmed by
  simulation (Node, 200 trials: the running sum ended negative in 100).
- **Where**: `crates/dsp/src/lib.rs`, `WindowedSignalMeter::snapshot`;
  `crates/engine/src/lib.rs`, `RmsWindow::rms`.
- **What is wrong**: both subtract the oldest square from a running `f64`
  sum. After signal followed by a full window of exact zeros the sum is a
  rounding residue of either sign; a negative residue makes `sqrt` return
  NaN. The dB field survives (`max` drops NaN), the linear `rms` does not,
  and `serde_json` writes NaN as `null`.
- **Why it was built that way**: the running sum avoids a pass over the
  window; the tests use short windows with exactly representable values.
  Both types are reachable only through `VoiceChainBlockProcessor`, which no
  production code constructs.
- **Fix**: clamp the sum with `.max(0.0)` before `sqrt`, or delete
  `VoiceChain`, `VoiceChainBlockProcessor`, `WindowedSignalMeter` and
  `RmsWindow` if the owner confirms they are dead.
- **Regression test**: 48 000 frames of a sine plus noise, then one window of
  zeros, for 50 seeds; require `rms == 0.0` (finite) each time.

### DSP-5 — EQ coefficient ramp counts samples, not frames

- **Severity**: Low. **Confidence**: Confirmed by reading.
- **Where**: `crates/dsp/src/lib.rs`, `Biquad::process_interleaved` calls
  `advance_ramp` once per sample.
- **What is wrong**: for an interleaved stereo biquad a ramp of `frames`
  finishes in `frames / 2` frames and the two channels of one frame use
  different coefficients. The engine uses one mono biquad per channel, so
  this is latent there; `GraphicEq::set_gain_db_ramped` on a two-channel
  instance is affected.
- **Fix**: advance the ramp when `index % channels == 0`.
- **Regression test**: a stereo biquad with a 64-frame ramp must reach its
  target after exactly 64 frames and give equal output for equal left and
  right input throughout.

### DSP-6 — Time Shift pause cuts to silence

- **Severity**: Low. **Confidence**: Confirmed by reading.
- **Where**: `crates/dsp/src/timeshift.rs`, `TimeShift::read_channel` and
  `begin_block`.
- **What is wrong**: resume and jumps fade in over 256 frames, but pause
  fills the output with zeros from the first sample of the block, which
  clicks on any non-zero signal.
- **Fix**: on the block where `paused` becomes true, read the delayed audio
  once more with a fade-out, then output silence.
- **Regression test**: a 100 Hz sine, post Pause, and require the largest
  sample-to-sample step in the pause block to stay below the sine's own
  maximum step times two.

### ENG-1 — Four hand-kept copies of the chain-processor list, one without Duck

- **Severity**: Medium (latent for new tools; one copy already differs).
  **Confidence**: Confirmed by reading; the Duck effect needs reproduction.
- **Where**: `crates/engine/src/lib.rs`: the two bypass lists in
  `compile_session_at_sample_rate_with_plugins_and_audio` (about lines 6094
  and 6120), the post-convergence loop in `compile_path_graph` (about line
  7606) and `is_chain_processor` (about line 8768). All use `matches!`, which
  compiles when a kind is missing. The copy in `compile_path_graph` has 21
  kinds; the others have 22: it omits `NodeKind::Duck`. A fifth list, the
  disabled-node arm at about line 6254, treats every kind it does not name
  as a dry bypass, which includes `Recorder`, `InputSwitch` and
  `OutputSwitch`.
- **What is wrong**: AGENTS.md requires an exhaustive `match` for kind
  classification. `renders_own_audio` follows that rule; these lists do not,
  so a new processor kind will compile and then fail in some layouts with
  "an audio combination the current engine cannot play".
- **Failure scenario to reproduce**: Mixer → Duck → output, with the Duck as
  the first node after the Mixer, compiled through
  `compile_mixer_fanout_session_with_plugins_and_audio`. If
  `tool_combinations.rs` already covers this through another branch of the
  compiler, record that and keep only the structural fix.
- **Why it was built that way** (inferred): each compiler entry point
  carries its own copy of the list, and the Duck repairs (AGENTS.md lessons
  of 2026-10-02 and issue #123) added Duck where a report failed, not
  everywhere. The UI mirror in `ui/src/draft.ts` (`isChainProcessor`) was
  already made exhaustive for the same reason.
- **Fix**: make `is_chain_processor` an exhaustive `match` with no `_` arm
  and call it from the three other sites. If Duck must stay excluded after a
  Mixer, express that as a second named function with a comment, not as a
  shorter copy. Give the disabled-node arm an exhaustive match too, and
  decide deliberately what a disabled switch or recorder does.
- **Regression test**: a test that iterates `NodeKind::ALL` and asserts the
  three former lists agree with `is_chain_processor` (it fails today for
  Duck), plus the Mixer → Duck → output compile above.
- **Prevention**: add a Clippy `disallowed_macros`-style guard or a source
  test that fails when `matches!(` appears with four or more `NodeKind::`
  variants outside tests (the scan used for this audit:
  nine sites in `crates/engine` and `crates/control`).

## Recording (`crates/recording`, `crates/control/src/recording*.rs`)

### REC-1 — WAV writer makes one write call per sample on an unbuffered file

- **Severity**: Medium (performance and robustness). **Confidence**:
  Confirmed by reading.
- **Where**: `crates/recording/src/lib.rs`, `WavWriter::write_interleaved`
  calls `self.output.write_all` for each 2, 3 or 4 byte sample.
  `crates/control/src/recorder_workers.rs`, `WavRecorderWorker` holds a
  `WavRecorder<std::fs::File>`; no `BufWriter` exists in either crate.
- **What is wrong**: a stereo 48 kHz recording issues 96 000 `WriteFile`
  system calls per second from the thread that drains recorders, followed by
  a `flush` per chunk. The cost grows with every active recorder (up to
  `MAX_ACTIVE_RECORDERS`).
- **Failure scenario**: several recorders, or an antivirus filter on the
  recording folder, make each drain pass slow; the recorder queue fills and
  takes fail with an overrun, or the control thread's requests lag.
- **Why it was built that way**: the writer is generic over `Write + Seek`
  and was tested against `Cursor<Vec<u8>>`, where per-sample writes cost
  nothing. The final header patch needs `Seek`, which a plain `BufWriter`
  makes awkward, so the file was passed directly.
- **Fix**: encode each chunk into a reused `Vec<u8>` inside
  `write_interleaved` and issue one `write_all` per chunk. This keeps the
  generic bound and the durability point (one flush per chunk).
- **Regression test**: a counting `Write + Seek` wrapper; writing a
  4 096-sample chunk must make at most two `write` calls. Keep the existing
  byte-for-byte file comparison.
- **Prevention**: the same counting wrapper in the FLAC and MP3 writer tests.

### REC-2 — One-click recording hard-codes 48 000 Hz

- **Severity**: Low. **Confidence**: Needs reproduction.
- **Where**: `crates/control/src/recording.rs`, `start_node_recording`:
  `sample_rate: 48_000` in the recorder config and
  `settings.split_minutes * 60 * 48_000` for automatic splitting.
- **What is wrong**: the rate is a literal instead of the running graph's
  rate. The multi-input worker used by the app always runs the graph at
  `INTERNAL_SAMPLE_RATE_HZ`, so the app is correct today. A worker activated
  at an endpoint rate through `activate_native_graph_candidate` would label
  44.1 kHz audio as 48 kHz (plays 8.8 % fast).
- **To reproduce**: activate a 44.1 kHz endpoint-rate worker in a control
  test, start a node recording, and read the WAV header.
- **Fix**: take the rate from the active runtime for the session (or use
  `INTERNAL_SAMPLE_RATE_HZ` by name and refuse node recording when the
  running graph's rate differs).
- **Regression test**: the reproduction above, expecting either the true
  rate in the header or a clear refusal.

### REC-3 — WAV writer omits the RIFF pad byte before the INFO chunk

- **Severity**: Low (latent: recorded frame counts are multiples of the
  128-frame quantum, so data sizes are even). **Confidence**: Confirmed by
  reading.
- **Where**: `crates/recording/src/lib.rs`, `WavWriter::finish_with_metadata`
  appends the `LIST` chunk at the end of the data chunk. `read_wav_metadata`
  in the same file skips a pad byte after an odd-sized chunk.
- **What is wrong**: a 24-bit mono file with an odd frame count has an
  odd-sized data chunk. The writer adds no pad byte, the crate's own reader
  expects one, and the title, artist and comment are lost on reload.
- **Fix**: write one zero byte after an odd data chunk before `LIST`, and
  include it in the RIFF size.
- **Regression test**: write 3 frames of mono PCM24 with a title, then
  `read_wav_metadata` must return the title.

### STO-1 — Deleting a session leaves its plugin node states behind

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/storage/src/lib.rs`, `Storage::delete_session` deletes
  from `sessions`, `session_history`, `graph_plans` and the active-session
  setting, but not from `plugin_node_states` (keyed by `session_id`,
  `node_id`).
- **What is wrong**: the rows stay for ever. `plugin_node_state_in_use`
  then reports the referenced state as in use, so
  `crates/control/src/plugins.rs` (about line 1684) never removes the state
  record or its file under `plugin-states`. A later session that reuses the
  ID (import or restore of the same session) silently receives the deleted
  session's plugin state on its nodes with the same IDs.
- **Why it was built that way**: `plugin_node_states` was added after
  `delete_session` (it is created in a separate `execute_batch` in
  `migrate`), and the schema declares no foreign keys, so nothing ties the
  table to `sessions`.
- **Fix**: delete the session's `plugin_node_states` rows in the same
  transaction, then let the control plane remove state records and files
  that are no longer in use.
- **Regression test**: save a session, set a plugin node state, delete the
  session, and require `plugin_node_states(session)` to be empty and
  `plugin_node_state_in_use(state)` to be false.
- **Prevention**: a storage test that lists every table with a `session_id`
  column from `sqlite_master` and fails when `delete_session` leaves a row in
  any of them, except tables named in an explicit keep-list (`recordings`).

### STO-2 — A failed backup leaves a partial file that retention keeps

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/storage/src/lib.rs`, `backup_connection` returns the
  SQLite error without removing `destination`; `restore_backup` in the same
  file does remove it. `prune_recovery_backups` keeps the ten newest files
  by name without checking them.
- **Failure scenario**: the disk fills during a daily backup. A truncated
  `audiorouter-backup-<date>.sqlite` remains. The same name cannot be
  retried ("must not already exist"), and the truncated file takes one of the
  ten retention slots, pushing out a good backup.
- **Why it was built that way** (inferred): `backup_connection` is a shared

- **Fix**: write to `<destination>.partial`, verify, then rename; remove the
  partial file on any error.
- **Regression test**: back up to a destination whose write fails part-way
  (a read-only directory after creation is not enough; use a destination on
  a path made unwritable mid-backup, or inject the failure by backing up
  from a connection closed underneath) and require no file at `destination`.
  A simpler deterministic variant: call the helper with a destination whose
  parent is removed after validation.

## Startup and sessions (`crates/storage`, `crates/control/src/sessions.rs`)

### STO-5 — One stored session that fails validation stops the whole backend

- **Severity**: High. **Confidence**: Confirmed by reading.
- **Where**: `crates/storage/src/lib.rs`, `list_sessions_after`,
  `load_history_before` and `load_session` run
  `deserialize_validated_session` on every row and return the first error
  for the whole call. `crates/control/src/persistence.rs`,
  `ControlPlane::try_with_storage` loads every session and its history with
  `?`, and `with_storage` panics on the error. `src-tauri/src/main.rs`,
  `start_owned_backend` catches the panic, counts a failure, restarts, enters
  safe mode after three, fails again and lets the backend thread exit.
- **What is wrong**: a single row that the current build rejects (a
  parameter range tightened in an update, a node kind renamed, a history
  entry written by a newer build, one damaged document) makes every session
  unavailable and leaves the tray running with no backend. `sessions.list`
  has the same all-or-nothing behavior at run time.
- **Failure scenario**: release N accepts a parameter up to 2 000; release
  N+1 validates 1 000. A user with one old session holding 1 500 updates and
  the app no longer starts, with only "storage initialization failed closed"
  in the log.
- **Why it was built that way**: validating on read is a fail-closed defence
  against a tampered or damaged database (the comment in `try_with_storage`
  explains the privacy-mute case). It treats every row like the privacy
  latch, although a bad session can be isolated without any safety cost.
- **Fix**: load rows one at a time. Keep a session that fails validation out
  of the graph store, record its ID and error in a `quarantinedSessions` list
  exposed by `status.get` and `system.diagnostics`, and show it in the UI
  with "export raw file" and "delete". A bad history entry is skipped, not
  fatal. Keep fail-closed only for the privacy mute and device-access
  latches.
- **Regression tests**: storage: insert one valid and one invalid session
  document directly with SQL; the listing returns the valid one and reports
  the other. Control: `try_with_storage` succeeds and `status.get` lists the
  quarantined ID. Shell: a `fresh_install_shell`-style launch on such a
  database reaches a served `status.get`.
- **Prevention**: a fixture directory of session documents from each
  released version, loaded by a test on every build, so a validation change
  that rejects old data fails CI before release.

### SES-1 — A refused delete still destroys version notes and the held comparison

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/control/src/sessions.rs`, `ControlPlane::delete_session`
  calls `clear_comparison(id)` and `forget_revision_notes(id)` before the
  "stop the session before deleting it" checks. `forget_revision_notes`
  (`saved_versions.rs`) deletes the persisted notes; `clear_comparison`
  (`compare.rs`) forgets the hold without republishing the graph, unlike
  `expire_comparison`.
- **Failure scenario**: the user presses Delete on a playing session. The
  request is refused, but the session's saved-version notes are gone, and a
  compare hold in progress never expires, so the playing audio stays in the
  compared state until the next save.
- **Why it was built that way** (inferred): the two cleanup calls sit at the
  top of the function, above guard clauses, as if added when those features
  arrived without re-reading the order of checks.
- **Fix**: move both calls after the last refusal and after the storage
  delete succeeds.
- **Regression test**: through `ControlPlane::dispatch`: add a version note,
  start the session, call `sessions.delete`, expect the refusal, then require
  `graph.versions` to still return the note.
- **Prevention**: in `delete_session`, keep all checks in one block that
  returns before any mutation, with a comment marking the line.

### SES-2 — A failed recorder finalize blocks Stop and Quit while audio keeps running

- **Severity**: High. **Confidence**: Confirmed by reading; the trigger (an
  I/O error while finalizing) needs a fault-injection test.
- **Where**: `crates/control/src/sessions.rs`, `session_stop`:
  `self.stop_node_recording(&node_id)?` runs before any worker is stopped.
  `crates/control/src/recording.rs`, `control_recorder_node`: when
  `worker.finalize` fails, the node's state becomes `Failed` and the error is
  returned; `stop_node_recording` then answers every later call for
  `Stopping | Failed` with "recorder needs recovery in the Recording tab
  before it can stop". `crates/control/src/safety.rs`,
  `dispatch_system_quit` refuses the same two states and also stops at the
  first `session_stop` error.
- **What is wrong**: stopping audio depends on closing a file. If the
  recording drive is full or unplugged, the first Stop fails, and every later
  Stop and Quit fails too. The microphone route stays live. Only starting a
  new recording on that node clears the state, which nothing tells the user.
- **Why it was built that way**: recorder finalization is ordered first so
  that "a failed recorder operation leaves the session and its endpoint
  available for explicit recovery" (comment in `session_stop`). That fits the
  session recorder with its explicit recovery flow; the one-click node
  recorders reuse the path, where the user's intent is simply to stop.
- **Fix**: in `session_stop` and `system.quit`, stop the audio workers
  first, then finalize recorders, collect recorder errors into the result
  (`recorders: [{ nodeId, state: "failed", reason }]`) and still return
  `state: "stopped"`. For `Failed`, drop the worker and keep the written
  file for the existing WAV/FLAC recovery.
- **Regression test**: a `RecorderWorker` test double whose `finalize`
  returns an error; attach it to a node, start the session, call
  `sessions.stop` through `ControlPlane::dispatch`, and require
  `state: "stopped"`, a stopped runtime, and a reported recorder failure.
  Repeat for `system.quit`.
- **Prevention**: a rule in the spec and a test for it: no failure outside
  the audio workers may prevent `sessions.stop` from stopping audio.

### SES-3 — Start can leave the session marked running with no audio

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/control/src/sessions.rs`,
  `session_start_with_candidate`: `&& self.maintain_application_capture(id, true)?`

## Task methods for assistants (`crates/control/src/simple.rs`)

### SIM-1 — Inserting or removing a node rewires to the wrong input and resets Mixer volume

- **Severity**: Medium. **Confidence**: Confirmed by reading.
- **Where**: `crates/control/src/simple.rs`, `simple_edit` for `nodes.add`
  (`between` and `after`) and `nodes.remove` (`bridge`), all through
  `connect`, which always picks the first free input of the target and a
  default channel matrix.
- **What is wrong**: the replaced connection's destination port, channel
  matrix and enabled flag are discarded. Three visible effects:
  1. Inserting between a source and a Duck's `key` input reconnects to the
     Duck's `in` input when that is free; the same for Input Switch side `b`.
  2. A Mixer stores each input's volume under a parameter named after the
     upstream node ID (`mixer_input_volume` in `crates/domain`). After an
     insert the Mixer's input comes from the new node, so the volume returns
     to 100 % and the old key stays in the parameters. Removing a node with
     `bridge` has the mirror effect.
  3. A custom channel matrix (for example left-only) becomes the default.
- **Failure scenario**: an assistant runs "add a compressor between Mic and
  the Mixer"; the mic's Mixer volume jumps from 40 % to 100 %.
- **Why it was built that way**: `connect` was written for the plain
  `connections.add` case ("first free input"), then reused for inserts.
- **Fix**: for inserts and bridges, build the new edges from the replaced
  edge: keep its destination port, matrix (when channel counts match) and
  enabled flag, and move the Mixer's per-input volume parameter to the new
  upstream ID.
- **Regression tests** (through `ControlPlane::dispatch`): insert between a
  source and a Mixer with volume 40 and require 40 afterwards; insert on a
  Duck `key` connection and require the new edge to end at `key`; remove
  with bridge and require the original port and volume.

- **Severity**: Low. **Confidence**: Confirmed by reading.
- **Where**: `crates/transport/src/lib.rs`, `dispatch_control_frame`: a raw
  frame from the hosting process is rate-limited under the user's SID. The
  window and the HTTP API both forward from that process, so they share the
  control plane's bucket (20 mutations per second, burst 40), and the HTTP

  require a window `sessions.stop` to succeed.
