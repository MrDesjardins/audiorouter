# 05 — Windows devices and application capture

Milestone ownership: M00 feasibility probes; M02 physical/process capture; M03 virtual desktop workflow; M07 recovery; M08 compatibility matrix.

## Platform facts and implications

WASAPI endpoint loopback captures the mix rendered to a selected output endpoint. Process loopback can include or exclude a specified process tree, and Microsoft's sample requires build 20348 or later. The latter capture is not tied to a single physical output. These are different source types with different provenance. [Microsoft endpoint loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [Microsoft process-loopback sample](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/ApplicationLoopback/README.md).

Capturing samples does not establish that ordinary application playback can be suppressed independently. v1 therefore offers capture-only plus explicit app/default-output selection to a virtual render endpoint. Do not implement “mute when capturing” by simply muting the app's Windows audio session: M00 must test whether doing so also silences the captured signal. This is a feasibility question, not a promised feature.

## Requirements

- **CAP-01 — Enumeration.** Enumerate physical and virtual capture/render endpoints with stable ID, name, direction, active/disabled/unplugged state, default roles, available channels/formats, and actionable access errors. Exclude arbitrary filesystem/process details from ordinary discovery output. Use endpoint notifications to update state without constant polling.
- **CAP-02 — Bindings.** A node binds either to an exact endpoint ID or explicitly follows `console`, `multimedia`, or `communications` default for its direction. Friendly names are not identity. Missing pinned devices remain missing until matched or deliberately replaced. Persist direction and channel expectations. Follow-default microphone selection requires explicit user choice.
- **CAP-03 — Physical capture.** Capture mono/stereo microphones and selected channels of a wider hardware endpoint into v1 mono/stereo ports. Negotiate shared-mode format and expose Windows conversions/enhancements when known. Handle access denied, microphone privacy disabled, exclusive ownership, unsupported format, and invalidated device separately.
- **CAP-04 — Output.** Render to multiple physical endpoints through independent bounded queues and clock correction. Per-output gain/mute does not change the Windows master volume. Default setup uses wired headphones; Bluetooth profile changes and high latency are surfaced and excluded from low-latency guarantees.
- **CAP-05 — Application picker.** List running audio applications with display name, PID, process creation time, executable/package identity, current activity, and capture capability. Allow advanced process selection without promising capture of every protected/background process. Do not identify a browser tab or website as a distinct capture source unless a later verified API supports it.
- **CAP-06 — Process capture.** Support inclusion of one selected process tree per source. Persist an executable/package-based selector, never PID alone. On restart, bind automatically only when exactly one verified matching instance exists; otherwise remain silent and return `ambiguousBinding`. Process name alone is insufficient. Support explicit `selectedInstance` and `allVerifiedInstances` policies; deduplicate overlapping parent/child trees before mixing.
- **CAP-07 — Exclusion boundary.** A separate advanced source may exclude one process tree where proven in M00. Do not present an arbitrary list of exclusions as a native capability: the documented mode targets one tree. Multiple exclusions remain future until a correct implementation is demonstrated. Reject unsupported combinations rather than falling back to capturing more audio than requested. [Microsoft mode definition](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode).
- **CAP-08 — Desktop capture.** Offer `Output device loopback` with the selected endpoint name and `Desktop In` virtual-render capture. Explain that endpoint loopback does not include sound rendered exclusively to other endpoints. Template defaults to the virtual render route for managed desktop playback; avoid recapturing the application's own headphone output.
- **CAP-09 — Playback policy.** Label app capture as “Keep normal playback” by default. Guided rerouting explains how to choose a virtual output in Windows/app settings and how to restore the prior choice. No blanket automatic app muting or unsupported per-app device forcing is required for v1. Store observed/manual routing context for duplicate-path warnings.
- **CAP-10 — Duplicate prevention.** Detect known overlaps: same endpoint loopback plus app capture, parent plus child capture, managed render source plus captured app known to render there, and monitored output recapture. Hard-reject proven feedback; warn with affected paths for potential duplicates. Dismissal belongs to a specific graph revision/context and is invalidated by relevant changes.
- **CAP-11 — Liveness.** Distinguish silent source, stopped application, disconnected endpoint, permission failure, and unsupported capture. A stopped app produces silence without deleting its node. PID reuse cannot bind a different executable. Reconnection uses bounded backoff and immediate endpoint/process events where available.
- **CAP-12 — System transitions.** Handle sleep/resume, default changes, USB reconnect, sample-rate change, Windows Audio service restart, and user session changes. Revalidate topology and permissions before resuming. Do not capture another logged-in user's audio intentionally; system-loopback scope limitations must be disclosed, with multi-user behavior tested before support claims.

## Acceptance and evidence

M00 records OS build, device driver, selected API, format, buffer period, HRESULTs, include/exclude results, and app restart behavior. Use controlled test apps as well as a browser and Discord; keep external app versions in evidence. M02 tests a 44.1 kHz device feeding the 48 kHz graph and a 48 kHz sink without progressive buffer growth. M03 proves the desktop bus avoids duplicate headphone playback. M08 reruns protected-content and unsupported-app cases for clear failure reporting; protected content capture is not a requirement.

v1 must not inject DLLs into games, hook protected processes, evade DRM, or alter anti-cheat settings. If an application cannot be captured, propose its ordinary output selection into a virtual render endpoint when supported.
